# ONBOARD — Outcome

## Problem

Agents that brainstorm an intake and agents that implement a task know nothing
about the project beyond what they read on the spot. Nobody has written down
the business rules, the invariants, the conventions the code follows or the
rules it must not break, so each agent rediscovers them, guesses, or misses
them:

- an intake misses a business rule the code already enforces, or contradicts
  one, and the user only finds out in review — if at all;
- a run's code works and passes its tests but ignores how the project names,
  structures, logs or handles errors, and breaks rules nobody stated (API
  compatibility, migrations, security);
- `zforge knowledge index` only records what intakes committed to (REQ and
  binding decisions, and whether they are built). A project with years of
  code and no intake yet has no knowledge at all;
- nobody checks the project's own test suite before the first run: a suite
  already red makes every run fail for reasons that are not the task's.

`zforge init` only writes configuration. There is no step between "zforge is
set up" and "write the first intake" that makes the project understood.

## Users

- **Tech lead / product owner** onboarding a project: gets a knowledge base
  drafted from the code, corrects and approves it, keeps it current.
- **Agent preparing an intake** (the intake skill): brainstorms on the
  approved knowledge instead of guesses, and flags where a stage contradicts
  it.
- **Agent implementing or reviewing a task** in a run: follows the project's
  conventions and rules, and the business rules of the area it changes.
- **Team members**: read the same knowledge, versioned with the code.

## Desired result

A project goes through an onboarding step, separate from `init`, that
checks the project can be worked on (its test suite runs, and how it
stands) and produces a knowledge base drafted from the whole codebase:
business logic, conventions, rules. Every statement in it points to the code
that shows it; what the code cannot show is asked, not assumed. The user
reviews and approves each file the way they approve an intake. From then on,
intakes are brainstormed on it and runs implement with it; when the code it
cites changes, zforge says which part is stale and redrafts only that part.

## Requirements

- REQ-001: Onboarding is a flow of its own (`zforge onboard`), not part of `init`. `init` stays fast, repeatable and never calls a model; run interactively, it ends by offering to start onboarding. Until a project is onboarded, `zforge status` names onboarding as the first next step.
- REQ-002: A probe, which calls no model, records at a pinned commit: language and toolchain, repository size, existing documentation (README, CLAUDE.md/AGENTS.md, ADRs and other docs), the state of the CodeGraph index, and one run of the project's test command — pass or fail, the failing tests, the duration.
- REQ-003: An agent drafts the knowledge from the whole codebase in three files: `domain.md` (entities, business rules, invariants, workflows and states), `conventions.md` (structure, naming, error handling, logging, patterns, how tests are written) and `rules.md` (what must or must not be done: security, compatibility, migrations, data). Only what is specific to this project goes in; general advice the skills already give does not.
- REQ-004: Every statement in the knowledge cites its evidence as `path:line` in the repository at the pinned commit. What the code cannot show — intent, a rule that is only implied — is written as an open question for the user, not as a statement.
- REQ-005: Each knowledge file goes through the same review as an intake file: numbered revisions, hashes, a decision log, `accept`/`revise` only by the user at a terminal. Only accepted revisions are approved knowledge; nothing else is fed to intakes or runs.
- REQ-006: The knowledge lives in the repository, in `docs/knowledge/` by default (configurable), and is committed with the code so the whole team and every machine share it.
- REQ-007: The intake skill reads the approved knowledge before drafting any stage, and a stage that contradicts approved knowledge says so for the user instead of silently deciding.
- REQ-008: A run's prompt includes the approved knowledge that applies to its task: conventions and rules always, and the parts of the domain for the areas the task concerns, within a size limit.
- REQ-009: The knowledge records the commit it was drafted from. A section whose cited files changed since is stale; `zforge status` and readiness say which. `zforge onboard refresh` redrafts only the stale parts, and they go through review again.
- REQ-010: Readiness also checks the project: approved knowledge present and not stale, and the baseline test run green or its failures recorded as known. By default a gap is a warning; a config setting makes it block a handover.
- REQ-011: The record of what intakes committed to — each REQ and binding decision with its implementation status — keeps working, generated next to the knowledge as a file of its own, apart from the knowledge the user approves.

## Must not change

- `init`, `install` and `migrate` stay deterministic and model-free; `init
  --force` stays safe to repeat.
- D1: accepting, asking for changes and handing over are the user's, at a
  terminal — for knowledge files as for intake files.
- A project that skips onboarding keeps working: intakes, readiness (warning
  only by default), runs.
- The commitments' semantics: `verified`, `integration_verified`,
  `integrated`, derived from records and git only.
- The run's rules on protected tests, budgets and the sealed output.

## Out of scope

- Environments, containers, devices and adapters (the v2 onboarding in
  `docs/v2/project-onboarding-and-local-testing.md`).
- Architecture and glossary files; they may come after the first three.
- Fixing a red baseline — onboarding reports it, the user decides.
- Several repositories as one project.
- Codex and OpenCode drafting the knowledge (Claude first).
- Generic coding advice that belongs in skills, not in project knowledge.

## Signs of success

- Onboarding backend-auth yields `domain.md`, `conventions.md`, `rules.md`
  where every statement has a `path:line` that shows it, and the unknowns are
  open questions; the user accepts all three.
- The probe reports the baseline test run, and a red suite shows up before
  any run, not as a failing run.
- An intake written after onboarding cites a rule from the knowledge, or
  says where it departs from it.
- A run's prompt carries the conventions and rules; a review finding can
  point to one of them.
- Editing a file the knowledge cites makes that section stale in `zforge
  status`; `zforge onboard refresh` redrafts it for review.
- A project that is not onboarded still reaches handover, with a warning.
