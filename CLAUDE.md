# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
cargo build                                       # build
cargo test --locked --all-targets                 # all tests (as CI runs them)
cargo test <name>                                 # single test (substring match)
cargo test -- --nocapture                         # tests with println output
cargo clippy --locked --all-targets -- -D warnings # lint (CI-enforced, warnings are errors)
cargo fmt --all                                   # format (CI checks `cargo fmt --all --check`)
cargo install --path . --locked --force           # install binary locally as `zforge`
```

## Architecture

zforge is a single Rust binary (`src/main.rs`) with these modules:

| Module | Purpose |

Thin: each parses, calls the library, prints |

A task gets at most one new run per invocation (`own`), and a task whose run cannot be created (e.g. budget used up) is reported and passed over (`refused`). Hidden `zforge run-worker --handover <H>`. `run cancel|log|wait <HANDOVER>`; cancel SIGTERMs the loop (SIGKILL after `CANCEL_GRACE`) then `ops::cancel`s its unfinished runs. A signal ends the loop with `Interrupted` (CLI exit 130). MCP `run_start` without `task` starts the loop in the background; `run_status|log|cancel` take a handover id. ### Global store and `install`

`zforge install` populates `~/.zforge/` with embedded agent definitions and skills (`embedded::store_files`). It and `install::ensure_global_store` (so every `init`) bring the store to the binary's version through `shipped::sync` (`src/shipped.rs`): `.shipped.json` in the root records `version` and, per store-relative path, the SHA-256 of what zforge wrote (written atomically after every sync). Per file: missing → written; equal → recorded; recorded and unchanged on disk → updated; recorded but changed → the user's edit, kept and reported (`kept your edit: …`); unrecorded (store from before the manifest) and differing → `Unrecorded::Replace` (store: old copy to `archive/<ts>/` at the same relative path, then written) or `Keep`. `--force` (`Mode::Force`) archives every differing file, then overwrites. Quiet mode (`init`) prints one stderr line when something changed or was kept. Init renders into the project through the same function, manifest `.zforge/.shipped.json`, archive `.zforge/archive/<ts>/` (`init::sync_project`): `--local` copies (unrecorded → Keep), `.claude/skills/zforge-*` (unrecorded → Replace when it carries the `generated-by` marker, else Keep) and every client's phase agents (`agent_render::materialize_agents_into`, unrecorded → Keep; `rerender_agents` after `models set` uses `Mode::Overwrite`, no archive). `zforge init` defaults to symlinking/referencing `~/.zforge/` (shared mode). Pass `--local` to copy everything into the project instead — for forks needing per-project customization.

### Multi-agent support

`zforge init --agent <target>` and `zforge mcp register --agent <target>` take `claude`, `codex`, `opencode` or `all`; `init` defaults to `claude`, `mcp register` to `all` (Claude is skipped when `claude` is not on PATH; the Codex/OpenCode config files are written either way). ### MCP server

`zforge mcp` runs as a stdio JSON-RPC server. Handlers call the library, not `cli::*` (whose functions print to stdout — the transport's own channel); `cli::output::divert_to_stderr` catches library progress. `zforge mcp register` writes the registration into the agent's config (Claude Code via `claude mcp add`, Codex `$CODEX_HOME/config.toml`, OpenCode `$XDG_CONFIG_HOME/opencode/opencode.json`); `init` does this automatically for Codex and OpenCode.

### Global project registry

`~/.zforge/registry.yaml` lists every zforge project on the machine. Schema: `current_project`, `projects[]` (`name`, `path`, `registered_at`, `registered_by: init|manual`, `agent_overrides`), `agents{}` (the command + args each runner is launched with; runs use `claude`), `fallback_policy` is gone (dropped by the global migration; the agent timeout is `execution.agent_timeout_secs` per project). Flags: `--no-register`, `--name <NAME>`, `--switch`. Same-path/same-name = no-op; same-path/different-name = rename (preserves `registered_at`, `registered_by`, `agent_overrides`); different-path/same-name = auto-suffix `-2`, `-3`, ….

### Models

**zforge names no model, only tiers** — models change faster than a built-in name could follow. The agent templates carry no `model:` and the `models.yaml` template is comments only. Every resolver (agent rendering, `reader::agent_model_for_phase_with_models`, `run::execute::model_for`) goes: `models.yaml` (project over global, per agent × phase field; `ModelsConfig::overlay`) → a `model:` the user wrote into the agent definition → `config::default_tier` — Claude only: `sonnet` for `code`, `opus` for `review`, Anthropic's aliases that follow new models → nothing (Codex/OpenCode run on their own default; no `model:` line). `inherit` (`config::INHERIT`) at any level means the client's own default: written into Claude's agent file, and no `--model` passed. `zforge models [--json]` shows each client × phase with its source (`project` / `global` / `agent definition` / `zforge default` / `client default`); `zforge models set <phase|all> <model> [--client C] [--global]` and `unset` edit `.zforge/models.yaml` or `~/.zforge/models.yaml` as text (`cli/models.rs::set_in_yaml`: comments kept, the result parsed back and checked before writing) and re-render the project's `.<client>/agents/` (`cli::init::rerender_agents`). `models.yaml` keys of removed phases (`spec`, `testspec`, `plan`) load and are ignored.

A run's agent argv (`run::execute::agent_spec`): headless bypass flags, the registered `args`, `--agent <phase>-agent`, `--model <X>`, `--max-budget-usd <left>`.

### Bounded child processes and cancel

**Bounded child processes (FIX-006)** — `src/process.rs::run_bounded` is the one place zforge runs a captured child; `spawn_agent` and `runner::run_with_language` both use it. Each child leads its own process group. Timeout → SIGTERM the group, `KILL_GRACE` (2s), SIGKILL. After the direct child exits, pipes are drained for at most `DRAIN_GRACE` (1s); if a descendant still holds them the group is SIGKILLed, and anything left in the group is killed before returning — no descendant outlives the call. Worst case: `timeout + KILL_GRACE + 2×DRAIN_GRACE`. (Previously only the direct child was killed and the reader threads were `join`ed until EOF, so a backgrounded grandchild held the wait open for its whole lifetime and kept running.) Children get stdin `/dev/null` unless input is supplied: a background process group reading the TTY would be stopped by SIGTTIN.

Because children are no longer in zforge's process group, group-directed signals (terminal Ctrl-C, `run cancel`) don't reach them directly. `process` installs a SIGINT/SIGTERM/SIGHUP handler (once, on first spawn) that forwards the signal to every active child group, waits up to `KILL_GRACE`, SIGKILLs survivors, then restores the default action and re-raises — zforge still dies of the signal as before. The escalation matters: non-interactive shells start `cmd &` jobs with SIGINT ignored. A background run's worker (`zforge run-worker`, own process group) sets `ZFORGE_CHILD_PGIDS_FILE` to `<run>/child-pgids`; `run cancel` SIGTERMs the worker group and every recorded child group, waits `CANCEL_GRACE` (5s) and SIGKILLs what is left (`process::terminate_process_groups`).

## Key invariants

- Paths from the config resolve through `Config`'s accessors (`skills_dir()`, `knowledge_dir()`, `project_root()`, … — backed by the private `resolve_path`): always absolute, `~` expanded, relative ones against the project root (parent of `.zforge/`), never cwd.
- `embedded.rs` is the single source of truth for bundled agents and skills; `cli::install` and `cli::init` both consume it.
- Registry mutations always pair `with_lock` (advisory `flock`) with `save_atomic` (tmp + fsync + rename). Never write `registry.yaml` directly. Reads (`io::load`) are lock-free and may observe a snapshot a few ms stale — acceptable for `status --global`.
- Tests touching the registry must set `ZFORGE_HOME` to a tempdir AND use `#[serial_test::serial]`. The env var is process-global; parallel tests will clobber each other.
- A run's `events.jsonl` is the only source of truth for its state; `run.yaml` is written once and `progress.md`/`result.md` are generated views. Never infer a run's state from anything else, and never report `verified` from what an agent wrote — it comes from a `verified` event with the candidate its verification tested.
- A run reads its contract only from the handover's pinned snapshots in the main checkout. The worktree's `.zforge/intakes/` is a committed copy nothing reads; editing the working files never changes a run in flight.
- Accepting a revision, asking for changes, handing over and recording known baseline failures are recorded only from a human at a terminal (stdin+stdout TTYs and a typed word — `intake accept|revise` and `onboard accept|revise|baseline` through `cli/confirm.rs`, `handover` with its own check in `cli/intake.rs`) or from the user's own `/accept`, `/revise`, `/handover` message read by the prompt hook (D1, amended 30/09/2026); no flag, env var or MCP tool bypasses them, and the model is denied the commands.
- `zforge run-worker` is internal (hidden in clap); users start background work with `zforge run … --async` or MCP `run_start`.
