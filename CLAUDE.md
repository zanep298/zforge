# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
cargo build                          # build
cargo test                           # all tests
cargo test <name>                    # single test (substring match)
cargo test -- --nocapture            # tests with println output
cargo clippy -- -D warnings          # lint (CI-enforced, warnings are errors)
cargo fmt                            # format
cargo install --path . --force       # install binary locally as `zforge`
```

## Architecture

zforge is a single Rust binary (`src/main.rs`) with these modules:

| Module | Purpose |
|--------|---------|

| `migrate/` | From the removed task pipeline to v1.5; nothing deleted — what goes, and a copy of every file rewritten, lands in `v1-archive/<ts>/` at the same relative path (`archive.rs`). `global.rs`: the store (retired templates/agents/skills archived; shipped agents/skills that differ refreshed, old copy archived; `registry.yaml` loses the fallback retry keys; `models.yaml` the removed phases) — run by `zforge install` and by `install::ensure_global_store` (so `init`), no-op once clean. `project.rs`: `plan` (task-pipeline records and files, v1 config keys, removed phases, clients to regenerate, backups — incl. the project's agents/skills in local mode) and `apply_files`; `cli/migrate.rs` (`zforge migrate [--dry-run] [--yes]`) shows the plan, asks (TTY or `--yes`), applies, then `init::run_for` the clients the project has with `force` (a CLAUDE.md/AGENTS.md the project wrote itself stays — `instructions.rs`). `yaml_text.rs` removes keys as text so comments survive (flow style → re-serialized). `status` and `init` point a project with v1 leftovers at `zforge migrate` (`needs_migration`) |

fenced blocks not counted), a requirement line over 25 words, a diagram drawn in text instead of ```mermaid. `brief.md` (`BRIEF_FILE`, created by `intake new` from `templates/intake/brief.md`) is the agent's one-page reading view in the user's language — not in `Intake::files()`, so never reviewed, linted or pinned. `graph.rs`: `zforge intake graph <ID>` prints the task dependency graph as Mermaid from each task's `depends_on`, so 04-breakdown never draws it by hand. `readiness.rs` (§6.2) checks the *accepted* snapshots — including `test_command` set and **no file accepted before something it builds on got a newer accepted revision** (D6; a blocking check, not a warning: stages rest on earlier stages, tasks on every stage and their dependencies); `readiness::stale` lists such files, and `review` accepts one of them unchanged as a new revision with the same hash so the user can confirm it again; `readiness::runtime` (the `claude` runner registered and on PATH) depends on the machine, so it is kept out of `check` and added by CLI `readiness`/`handover` and MCP `readiness` via `Readiness::with`; `handover.rs` writes `.records/handovers/HANDOVER-nnn.json` after re-checking under the lock against the revisions the user confirmed; `knowledge.rs` builds `.zforge/knowledge/index.{md,json}` (decision active/superseded vs implementation not_implemented/handed_over/verified/integration_verified/integrated — the highest that holds; `integrated` = the output of a verified integration run of a handover holding the requirement's task is an ancestor of the manifest's baseline branch *now* (`git merge-base --is-ancestor`), recomputed on every build and never stored, so a squash/rebase merge stays `integration_verified`; `entry.integration` names handover, run, candidate, commit, branch). CLI `cli/intake.rs`: `intake new|task|status|review|accept|revise`, `readiness`, `handover`, `knowledge index`. **`accept`, `revise` and `handover` require stdin+stdout TTYs and a typed confirmation — never add a flag or env var to bypass it**; the generated `.claude/settings.json` also denies them. Config: `knowledge.baseline` (default `main`), `execution.max_iterations`, `execution.budget_usd` |
| `run/` | v1.5 Mốc B (intake `MOC-B`). `.zforge/runs/RUN-nnn/` holds `run.yaml` (written once with `create_new`; ids claimed by creating the directory, so concurrent creates never share one) and append-only `events.jsonl` — the only source of truth: `RunState::replay` follows workflow §6.1 and `Run::append` refuses, under the run's lock, any event the state machine disallows; final states stay final. A torn last line is ignored, any other unreadable line is an error, and an append after a torn line cuts it first. `contract.rs` loads the handover manifest and every snapshot it pins, verifying each SHA-256 — a tampered snapshot stops the run before anything is created — and renders `templates/contract.tmpl` from those snapshots only. `worktree.rs` gives each run `.zforge/worktrees/<RUN>` on `zforge/<task>/<run>` from `RunMeta::start_commit()`, keeping the user's checkout untouched (`.gitignore` gains the line only when git does not already ignore it) and keeping the branch when the worktree is removed. `execute.rs` drives `orchestrator::iterate` with flow `Contract`: Claude headless in the worktree via `spawn_agent_in`, `--max-budget-usd` = what is left of the budget shared by every run of that task in the handover, `attempt_started` holding the allotment in flight (a call killed mid-flight counts it all), a trace per call, `verified`/`verify_failed` carrying the worktree's fingerprint, and `blocked` on budget or on a change request the agent wrote (§8). The agent gets what the worktree lacks (`agent_env.rs`): layer 1, the code phase's checklists (`claude_skills::sources_for("code", language)` — the same catalog that fills `code-agent`'s `skills:`) named in the prompt by absolute path in `config.skills_dir()`, readable by any client; layer 2, Claude's `.claude/agents`, `.claude/skills` and `.claude/settings.json` (permission rules, hooks) copied from the main checkout when the worktree lacks them **and git ignores them** (so the seal cannot commit them) — neither committed nor ignored is left out with a warning, since the output would carry it. A pass counts only if no protected test file differs from where the agent started (`guard.rs`: `execution.protected_tests` globs, default conventional test locations, plus files the test command names; modified/deleted/renamed-away — additions are fine; a task's `tests_may_change` frontmatter, accepted by the user, exempts paths); otherwise it is recorded `verify_failed` with `protected test changed: <path>` and fed back to the agent. With `execution.review: true` (off by default), a pass is then reviewed (`review.rs`, workflow §7): a second agent call — phase `review`, `review-agent` when the worktree has it, the review model from models.yaml — gets `templates/review_contract.tmpl` (contract, stages, `git diff <start>`) and must end with `VERDICT: APPROVE` or `VERDICT: CHANGES` after `- ` findings; `review_started`/`reviewed` events account its cost like an attempt (in flight → reported or whole allotment). Anything but an approval — changes, no verdict, a failed call, or a reviewer that changed the worktree's fingerprint — is recorded as `verify_failed` with `review: <finding>` and fed back to the coder; no budget left for the review blocks the run. `execute::call_agent` is the one agent call (spec, spawn, trace, cost) for both phases. On a pass, `output.rs::seal` (MOC-C TASK-001) commits whatever the agent left uncommitted and accepts it only if the worktree is then clean with the same fingerprint; that commit is recorded as `verified.commit` — the run's output, which dependent tasks start from — and `RunState.output`. `git.rs` is the one git wrapper for runs (repo-bound `GIT_*` stripped); zforge's commits use a fixed identity and **always run the repository's hooks** — a rejecting hook fails the seal. `start.rs` (TASK-002): a task with `depends_on` starts from its dependencies' outputs — the newest verified run of each in the same handover — recorded once as `run.yaml` `start { commit, from: [{task, run, commit}] }` (absent = baseline, so Mốc B run files are unchanged); several dependencies are merged in the worktree in the order the task lists them, and a conflict aborts the merge and fails the run naming tasks and files, before any agent call. A dependency without output refuses the run before anything is created. `integrate.rs` (TASK-003): `zforge run <HANDOVER> --integration` records a run with `kind: integration` (`task: integration`, branch `zforge/<INTAKE>/integration/<RUN>`, budget 0) once every handed-over task has a verified output; its worktree holds the outputs of the leaf tasks (no other task depends on them — `contract::Handover::leaves`), merged like a dependent task's start. It runs `checks` recorded in `run.yaml` — the first code block under "Integration verification" (or the legacy "Kiểm chứng tích hợp") in the pinned breakdown, HTML comments dropped first (the template's example block sits in one; a `#` line inside the block is a comment), else `project.test_command` — one `sh -c` per line via `run_bounded`, 1800s each, output in `<run>/checks.log`; the first failure fails the run, all passing seals the tree as its output. No agent is called. `execute::execute` and `ops::retry` dispatch on `kind`; task lookups (outputs, spending, knowledge) ignore integration runs. `feature.rs` (TASK-004): `FeatureState::derive` is a pure function of the manifest's tasks, their `depends_on` and the run records — per task `waiting {on}` (empty = ready) / `running` / `verified {run, commit, from, outdated}` / `stopped {run, status, reason}` / `blocked {by}`, plus the integration; the newest verified run wins over later failures, a stopped task blocks everything downstream (`by` names where the chain stopped), and `outdated` marks work built on a dependency output that a newer verified run has replaced. There is **no feature state file**. `feature::load` refreshes the handover's runs and derives; `zforge run status <HANDOVER> [--json]` prints it (`view::feature`), an id not ending in `HANDOVER-…` is a run (`run::is_handover`). `feature_ops.rs` (TASK-005): `zforge run <HANDOVER> [--async]` loops on `next_step(FeatureState)` — ready task → new run; latest run `cancelled` or `failed` with reason `interrupted…` → retry (`retry_of`); `failed`/`blocked` are verdicts and stay; `running` elsewhere stops the loop; all verified → integration — so re-running the command resumes. A task gets at most one new run per invocation (`own`), and a task whose run cannot be created (e.g. budget used up) is reported and passed over (`refused`). Locks under `.zforge/runs/.locks/<INTAKE>/`: `<HANDOVER>.loop` for the loop's lifetime, and `claim(<HANDOVER>/<TASK>)` around every run creation (`--task`, `--integration` too), refusing while that task has a run not yet final. `.zforge/runs/features/<INTAKE>/<HANDOVER>/` holds only `pid` (removed at exit), a background loop's `launch.pid` and `log` — never state. Hidden `zforge run-worker --handover <H>`. `run cancel|log|wait <HANDOVER>`; cancel SIGTERMs the loop (SIGKILL after `CANCEL_GRACE`) then `ops::cancel`s its unfinished runs. A signal ends the loop with `Interrupted` (CLI exit 130). MCP `run_start` without `task` starts the loop in the background; `run_status|log|cancel` take a handover id. Note the Mốc B budget rule: an attempt killed mid-call counts its whole allotment — all the task had left — so a task cancelled while its agent works cannot run again in that handover. `reuse.rs` (TASK-006): before a task's first run in a handover, the loop looks for a verified run of it in another handover of the intake with the same `contract_key` (SHA-256 over the baseline commit, the 4 stages, the task file and every transitive dependency's task file, as pinned) **and** that started from exactly the outputs its dependencies have now; found, it records a run whose only event is `reused {from_run, from_handover, candidate, commit}` (ready → verified, no worktree, no cost, branch = the reused run's). `RunState.reused_from` / `Progress::Verified.reused_from` show it (`reused` label). Only the loop reuses; `--task` always runs, and integration runs are never reused. Tests: `tests/run_test.rs` (per task) and `tests/feature_run_test.rs` (MOC-C acceptance: the five success signals, two dependencies, an agent-requested amendment, checkout unchanged) share the stub project in `tests/support/run_project.rs` (`#[path]` module, not a test crate). `ops.rs` adds background runs (hidden `zforge run-worker`, `launch.pid`, `child-pgids`), `refresh` (interrupted worker — stopping the groups it left — or a run that never started), cancel (signal the worker itself, then the groups, sharing `process::terminate_process_groups`), retry, and clean (commits leftovers to the run's branch, keeps the branch). `view.rs` generates `progress.md`/`result.md`. CLI `cli/run.rs`: `zforge run <HANDOVER> --task <T> [--async]`, `run status|list|cancel|retry|clean`. `process::catch_interrupts` makes Ctrl-C record `cancelled` and exit 130 instead of re-raising |
| `trace/` | IMP-006. One `PhaseTrace` per agent call of a run in `<run>/trace.jsonl`: `expected` (named agent, model, the agent's preloaded skills, CodeGraph when `.codegraph/` exists — built by `orchestrator::trace_record`) kept apart from `observed`, which `claude.rs` reads from claude's `stream-json` (init event: version/model/MCP status/agent+skill catalogs; every `tool_use` incl. subagents'; `permission_denied`; `result`; stderr warnings about dropped config). Findings are tagged `infrastructure` / `agent_choice` / `run`; `not_observable` lists what Claude cannot show (whether `skills:` were preloaded). Non-claude runners and interactive runs get an `unavailable` record. `zforge run status` shows them (`trace::text`). Fixture: a real 2.1.278 stream in `tests/fixtures/claude/` |
| `config/` | Loads `.zforge/config.yaml` (walks up from cwd): project (name, language, test command), `runner.default`, `paths.agents`/`paths.skills`, `execution` (`max_iterations`, `budget_usd`, `protected_tests`, `review`, `agent_timeout_secs` — a safety net, default 3600: a call zforge kills counts its whole allotment, so the budget should stop a working agent first), `knowledge.baseline`. Keys of the removed task pipeline load and are ignored. Also `models.yaml` (`ModelsConfig`), `PHASES` = `code`, `review`, `default_tier`, `INHERIT` |
| `embedded.rs` | Agent definitions (`code-agent`, `review-agent`) and skill bundles baked in via `include_str!()`. Each agent repeats the run prompt's standing rules (so they hold without it, e.g. used outside a run) plus what to do outside a run; a test checks agent and prompt name the same change-request sections, test rules and verdict lines. `review-agent` has `disallowedTools: Edit, Write, NotebookEdit` (read-only by configuration; `agent_render::without_claude_keys` drops it for Codex/OpenCode); consumed by `init` and `install`. Run prompts (`templates/contract.tmpl`, `review_contract.tmpl`) are embedded by `run::contract` |

### Global store and `install`

`zforge install` populates `~/.zforge/` with embedded agent definitions and skills. Run once per machine; rerun after upgrading to refresh. `zforge init` defaults to symlinking/referencing `~/.zforge/` (shared mode). Pass `--local` to copy everything into the project instead — for forks needing per-project customization.

### Multi-agent support

`zforge init --agent <target>` and `zforge mcp register --agent <target>` support `claude` (default), `codex`, `opencode`, or `all`. Agent detection in `cli/init/detect.rs` also auto-detects project language (Rust, Go, Flutter, etc.) to select appropriate skill bundles.


### `zforge init` scaffolding

Templates are embedded via `embedded.rs`. Init writes `.zforge/`, `CLAUDE.md` / `AGENTS.md`, `.claude/settings.json`, per-client agent definitions (`.claude/agents/`, `.codex/agents/`, `.opencode/agents/`), and `.claude/rules/`. `init.rs` orchestrates; the pieces live in `cli/init/`:

| Module | Owns |
|--------|------|
| `store_paths.rs` | `StorePaths` — where agents/skills are, for config.yaml **and** every instruction file. Shared mode names the real global store (`$ZFORGE_HOME` aware, via `embedded::global_store_dir` = `registry::paths::registry_dir`); local mode `.zforge/skills`. Templates reference skills only through `{{skills_dir}}` (FIX-013). |
| `config_file.rs` | `.zforge/config.yaml` ownership (FIX-017): created once from the template; on re-init only the managed keys `runner.default`, `paths.agents`, `paths.skills` change. `models.yaml` is never overwritten, even with `--force`, which now means "refresh generated files" only. Managed keys are edited in the text, so comments and layout survive (fallback to re-serializing for layouts the line editor cannot handle). |
| `claude_settings.rs` | `.claude/settings.json` is shared with the user: created from the template when missing, left alone without `--force`, and on `--force` *merged* — every existing key and allow entry kept in order, zforge's missing allow entries appended, only retired zforge entries (pre-0.9 CodeGraph tool names) removed. Invalid JSON is reported, never clobbered. `serde_json` has `preserve_order` so key order survives |
| `runner.rs` | Default runner (FIX-015): `--default-runner` (must be a scaffolded client) → the only client → with `--agent all`, first of claude → codex → opencode on `$PATH`. Written to `runner.default`. Registry seeding covers exactly the scaffolded clients. |
| `claude_skills.rs` | IMP-004 (Claude). The CLAUDE.md skills section (`{{claude_skills_section}}`) is generated from the same catalog. ### MCP server

`zforge mcp` runs as a stdio JSON-RPC server. Handlers call the library, not `cli::*` (whose functions print to stdout — the transport's own channel); `cli::output::divert_to_stderr` catches library progress. `zforge mcp register` writes the registration into the agent's config (Claude Code via `claude mcp add`, Codex `$CODEX_HOME/config.toml`, OpenCode `$XDG_CONFIG_HOME/opencode/opencode.json`); `init` does this automatically for Codex and OpenCode.

### Global project registry

`~/.zforge/registry.yaml` lists every zforge project on the machine. Schema: `current_project`, `projects[]` (`name`, `path`, `registered_at`, `registered_by: init|manual`, `agent_overrides`), `agents{}` (the command + args each runner is launched with; runs use `claude`), `fallback_policy` is gone (dropped by the global migration; the agent timeout is `execution.agent_timeout_secs` per project). Mutations go through `registry::lock::with_lock` (advisory `flock` on `~/.zforge/registry.lock`) + `registry::io::save_atomic` (tmp + fsync + rename). `paths.rs` honors `ZFORGE_HOME` so integration tests can redirect to a tempdir — combine with `#[serial_test::serial]` because the env var is process-global.

`zforge init` calls `registry::auto::auto_register` at the tail of `run()` after local scaffold succeeds. Failure is non-fatal: scaffold is the contract, registry is best-effort. Flags: `--no-register`, `--name <NAME>`, `--switch`. Same-path/same-name = no-op; same-path/different-name = rename (preserves `registered_at`, `registered_by`, `agent_overrides`); different-path/same-name = auto-suffix `-2`, `-3`, ….

`zforge project` (CLI) and the matching MCP tools share `cli::project::{add_entry, remove_entry, purge_zforge_dir, switch_to, list_data}` — no parallel code paths. `zforge status --global` reads every registered project in parallel (see `status.rs`).


### Models

**zforge names no model, only tiers** — models change faster than a built-in name could follow. The agent templates carry no `model:` and the `models.yaml` template is comments only. Every resolver (agent rendering, `reader::agent_model_for_phase_with_models`, `run::execute::model_for`) goes: `models.yaml` (project over global, per agent × phase field; `ModelsConfig::overlay`) → a `model:` the user wrote into the agent definition → `config::default_tier` — Claude only: `sonnet` for `code`, `opus` for `review`, Anthropic's aliases that follow new models → nothing (Codex/OpenCode run on their own default; no `model:` line). `inherit` (`config::INHERIT`) at any level means the client's own default: written into Claude's agent file, and no `--model` passed. `zforge models [--json]` shows each client × phase with its source (`project` / `global` / `agent definition` / `zforge default` / `client default`); `zforge models set <phase|all> <model> [--client C] [--global]` and `unset` edit `.zforge/models.yaml` or `~/.zforge/models.yaml` as text (`cli/models.rs::set_in_yaml`: comments kept, the result parsed back and checked before writing) and re-render the project's `.<client>/agents/` (`cli::init::rerender_agents`). `models.yaml` keys of removed phases (`spec`, `testspec`, `plan`) load and are ignored.

A run's agent argv (`run::execute::agent_spec`): headless bypass flags, the registered `args`, `--agent <phase>-agent`, `--model <X>`, `--max-budget-usd <left>`.

### Bounded child processes and cancel

**Bounded child processes (FIX-006)** — `src/process.rs::run_bounded` is the one place zforge runs a captured child; `spawn_agent` and `runner::run_with_language` both use it. Each child leads its own process group. Timeout → SIGTERM the group, `KILL_GRACE` (2s), SIGKILL. After the direct child exits, pipes are drained for at most `DRAIN_GRACE` (1s); if a descendant still holds them the group is SIGKILLed, and anything left in the group is killed before returning — no descendant outlives the call. Worst case: `timeout + KILL_GRACE + 2×DRAIN_GRACE`. (Previously only the direct child was killed and the reader threads were `join`ed until EOF, so a backgrounded grandchild held the wait open for its whole lifetime and kept running.) Children get stdin `/dev/null` unless input is supplied: a background process group reading the TTY would be stopped by SIGTTIN.

Because children are no longer in zforge's process group, group-directed signals (terminal Ctrl-C, `run cancel`) don't reach them directly. `process` installs a SIGINT/SIGTERM/SIGHUP handler (once, on first spawn) that forwards the signal to every active child group, waits up to `KILL_GRACE`, SIGKILLs survivors, then restores the default action and re-raises — zforge still dies of the signal as before. The escalation matters: non-interactive shells start `cmd &` jobs with SIGINT ignored. A background run's worker (`zforge run-worker`, own process group) sets `ZFORGE_CHILD_PGIDS_FILE` to `<run>/child-pgids`; `run cancel` SIGTERMs the worker group and every recorded child group, waits `CANCEL_GRACE` (5s) and SIGKILLs what is left (`process::terminate_process_groups`).

## Key invariants

- All paths go through `Config::resolve_path()` — always absolute, always relative to the project root (parent of `.zforge/`), never to cwd.
- `embedded.rs` is the single source of truth for bundled agents and skills; `cli::install` and `cli::init` both consume it.
- Registry mutations always pair `with_lock` (advisory `flock`) with `save_atomic` (tmp + fsync + rename). Never write `registry.yaml` directly. Reads (`io::load`) are lock-free and may observe a snapshot a few ms stale — acceptable for `status --global`.
- Tests touching the registry must set `ZFORGE_HOME` to a tempdir AND use `#[serial_test::serial]`. The env var is process-global; parallel tests will clobber each other.
- A run's `events.jsonl` is the only source of truth for its state; `run.yaml` is written once and `progress.md`/`result.md` are generated views. Never infer a run's state from anything else, and never report `verified` from what an agent wrote — it comes from a `verified` event with the candidate its verification tested.
- A run reads its contract only from the handover's pinned snapshots in the main checkout. The worktree's `.zforge/intakes/` is a committed copy nothing reads; editing the working files never changes a run in flight.
- Accepting a revision, asking for changes and handing over are recorded only from a human at a terminal (stdin+stdout TTYs and a typed confirmation) or from the user's own `/accept`, `/revise`, `/handover` message read by the prompt hook (D1, amended 30/09/2026); no flag, env var or MCP tool bypasses them, and the model is denied the commands.
- `zforge run-worker` is internal (hidden in clap); users start background work with `zforge run … --async` or MCP `run_start`.
